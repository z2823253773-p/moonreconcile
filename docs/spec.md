# 表格对账与差异解释工具：设计稿 v2

初稿日期：2026-09-29；本次修订：2026-09-30  
状态：按用户反馈修订的产品规格；尚未实现，需求与性能待验证。本文不是已完成成果说明，也不代表通过赛事初审。

## 1. 产品目标与本次修改

用户已选择“表格对账与差异解释”方向。产品帮助用户核对来自两个系统或两个时间点的表格，完成 **导入 → 列映射与规则配置 → 记录对应 → 字段差异解释 → 人工复核 → 最终报告导出**。

有可靠共同主键时直接核对；没有可靠主键的剩余记录可以生成候选对应，由用户确认。产品价值同时包括“哪些记录对应”“哪些内容不同”“哪些不同属于已声明的可接受变化”和“哪些问题仍未解决”。

上一版把整个产品收窄成小表模糊匹配，无法充分回应 MoonTick 被指出的“选题过窄、功能面太薄、场景较特殊”。本次修改：

- 将列映射、业务字段规则、结构差异、人工决策回导和最终报告纳入首版必需功能；
- 取消整表最多 100 行、最多四个匹配字段、字段最多 64 字符和必须设置阻塞字段的统一限制，按输入大小和复杂匹配计算量分别设置保护；
- 明确订单核对、迁移验收、商品目录对应三个不同工作流；
- 将模糊匹配作为剩余记录的辅助环节，首版候选必须经人工接受才成为正式对应；
- 保留一对一关系边界，但根据真实输入需求决定是否补 XLSX 读取适配，不把 CSV 当作永久产品边界。

以上是设计决策，不是已实现功能或审核通过承诺。增加模块本身不能替代需求证据和可运行成果。

## 2. 现有工具与差异化假设

前序查阅的 MoonRow 0.1.0 文档显示，它已有 CSV 组合主键比较、重复键诊断、新增/删除/修改识别及报告。MoonVerity 提供数据契约和质量检查，NyaCSV 提供 CSV 解析。MoonFrame 的完整能力仍需进一步审计，不能据此声称本项目填补了确定的生态空白。

本项目拟验证的区别是：在一个可复用 MoonBit 核心与 CLI 中，串联显式列映射、业务比较规则、剩余记录候选、人工决定回导和可追溯报告。精确比较是必要基础，不能单独作为创新点；多个输出格式也不单独计作业务能力。

实施前以真实流程比较 MoonRow、DataComPy 和 Python Record Linkage Toolkit 等已有方案的覆盖情况。若简单的精确关联加现有工具即可完成流程，且新工具未减少可观察的配置或复核成本，应考虑扩展已有项目，不为参赛硬造独立工具。现阶段没有真实用户接入、节省工时、匹配准确率或完整竞品审计结果。

## 3. 三个目标工作流

| 工作流 | 输入和常见问题 | 首版支持的处理 | 用户据此采取的行动 |
| --- | --- | --- | --- |
| 两套订单系统核对 | 每份表每单一行；订单 ID 可对应，但列名、状态写法、金额和日期表达不同；某侧漏同步 | 列映射、唯一键对应、状态映射、金额/日期规则、单边记录和差异明细 | 定位需要调查或补同步的订单，保存复核结果 |
| 系统迁移前后验收 | 迁移前后导出表；列被改名或移除，字段转换，记录遗漏，部分键异常 | 结构检查、明确允许的转换、逐字段核对、异常键诊断、必要时人工对应 | 区分预期转换与实际问题，决定接受迁移或返工 |
| 两家供应商商品目录建立对应 | 两侧 ID 不同；品牌、名称、规格可比较，可能存在多个相似商品 | 可选分组、候选评分、竞争关系展示、一对一建议、人工确认 | 导出明确标注来源的商品对应表，并保留未解决项 |

三个场景共享同一套引擎，但输入假设、规则和输出决策不同。订单场景不涵盖拆单、合单或多笔付款匹配；迁移场景不限于丢失 ID 的抽样；商品目录场景不声称仅凭名称即可确定身份。

目前这些是待验证场景。演示应明确标注合成、公开来源或经许可脱敏的数据，不能将合成演示称为真实用户案例。至少取得一个可复现真实工作流程，是本项目内部的继续投入依据，并非官方额外报名条件。

## 4. 首版必须形成的功能闭环

1. **导入与检查**：读取两份 UTF-8 CSV，校验标题、重复列名、行宽、编码、必需列和资源预算；错误定位到文件、逻辑记录和字段。
2. **映射与规则**：声明左右列到逻辑字段的对应、可选组合键、身份匹配字段、内容比较字段、显式转换和忽略列。匹配字段与比较字段可以不同。
3. **记录对应**：先用有效且唯一的键确定对应；无键或异常键记录进入剩余集合，按配置生成候选或交人工处置。
4. **差异解释**：逐字段展示原值、规则处理后的值、规则名称、差值与容差，以及“相同、规则下等价、不同、无效值”的结论。
5. **人工复核**：导出候选和决策模板，支持接受、拒绝、确认单边无对应，再导入决定并检查冲突。
6. **最终导出**：输出机器可读 JSON、记录对应 CSV、字段差异 CSV、Markdown 汇总和仍待处理清单，保留规则和决策依据。

仅完成相似度函数、最优匹配或差异报告，不能称为完成首版。实现以可复用 MoonBit 核心库和 CLI 为主，图形界面不是首版前提。

CSV 解析优先评估复用 NyaCSV；先实际验证畸形输入、引号和换行、空字段、原值保留与报错行为，再固定版本，不因文档存在就假定所有输入契约已满足。

**XLSX 的处理条件**：真实使用者能可靠导出 CSV，且不会破坏前导零、日期和数值时，CSV 可作首个入口。若真实流程只有 XLSX，或转换本身丢失必要信息，则只读工作表适配成为该场景交付前提，需重新估算工作量。首版不承诺公式重算或恢复文件中本已丢失的信息。

## 5. 字段比较语义

### 5.1 映射与结构

每个逻辑字段明确指定左右来源列和类型，禁止含糊重复映射。必需来源列不存在属于配置或输入错误。未映射且未显式忽略的列必须进入结构差异报告，不能静默视为全部核对完成；忽略列也列入汇总以便审查。

转换只能按配置执行：首尾 ASCII 空白清理、ASCII 小写转换、有限值映射表、明确的缺失值标记。值映射单次执行，不递归连锁替换。不自动猜测类型、货币、日期格式、主键或 Unicode 规范化方式。原值始终保留。

### 5.2 内容比较规则

| 类型 | 规则 | 必须解释的边界 |
| --- | --- | --- |
| 文本/标识符 | 默认原样比较，可显式转换后比较 | `001` 与 `1` 默认不同，不能把编号转成数值 |
| 十进制数 | 精确十进制运算；`abs(a-b) <= max(abs_tol, rel_tol * max(abs(a), abs(b)))` 为容差内 | 两种容差非负、默认均为 0；保留差值和实际阈值，不用二进制浮点代替金额语义 |
| 日期 | 严格解析有效日历日期 `YYYY-MM-DD`，按绝对天数差比较 | 天数容差默认 0；不猜月日顺序，不推断时区或时间戳 |
| 缺失值 | 双方缺失默认视为内容相等，可配置为需处理；单方缺失为差异 | 空串是否为缺失须明示；`0` 不隐式等同空值 |

初始十进制语法允许可选正负号、整数和可选小数部分，不含科学计数、千分位或货币符号；输入最多 64 位数字、小数最多 18 位。采用十进制数字/字符串运算或经验证等价方案，中间运算不截断；越界明确报错。这是待验证的实现契约，尚无数值测试结果。

类型解析失败输出 `invalid_value`，不能偷偷改成字符串比较。规则处理后等价但原值不同，输出 `equivalent_by_rule` 并保存转换依据。例如 `100.00` 与 `100` 在十进制规则下等价，状态 `paid` 与 `已支付` 只有显式映射后才等价。

“差异解释”仅解释观察到的字段变化和触发的规则。例如“金额相差 0.02，超过配置容差 0.01”；不能由此推断“财务漏记”之类未经证实的业务原因。

## 6. 记录对应与计算预算

### 6.1 精确对应

组合键为可选项。按声明的规范化规则处理后，键各部分有效、非缺失，且在左右两侧各出现一次，才自动建立 `exact_key` 对应。重复键、缺失键明确诊断，不采用“取第一条”。不设置键时全部记录进入剩余集合。

没有剩余记录时跳过候选阶段，不要求用户配置匹配字段。剩余记录可选择进入候选流程，或直接列为待人工处理；不会因为没有候选就自动判定客观上无对应。

### 6.2 候选生成与评分

分组/阻塞字段是可选优化：同一规则内各条件同时成立，多条规则之间取候选并集并去重。缺失分组值或不满足规则的记录继续显示为待处理。报告说明候选覆盖受配置影响，不宣称规则以外不存在正确对应。

未设置分组时，在预算内允许剩余记录两两比较。超过预算时停止该阶段，明确标记未完成并提示缩小候选范围，不静默截断候选列表。

可选择的身份匹配计分包括精确文本、归一化编辑相似度、十进制容差内/外、日期容差内/外。精确相等或满足类型容差计 10000 分，否则计 0 分；编辑相似度按 Unicode 码点计算：

`floor(10000 * (max_length - edit_distance) / max_length)`。

双方为空或任一方缺失时，身份匹配分数为 0，不能靠“共同缺值”证明身份；这与内容比较中双方缺失可视为相等是两个不同问题。类型无效的候选不能自动得到有效总分，需保留诊断和人工处理入口。

字段权重为 1–10000 的整数，总分使用固定分母的加权平均并向下取整，缺失字段不自动从分母删除。最低候选阈值为 1–10000。分数表示配置下的相似程度，不是概率、准确率或已校准置信度。配置中启用候选评分时必须至少有一个有效匹配字段，并校验整数累加溢出。

### 6.3 一对一建议

对合格候选图的每个连通分量，采用带未匹配虚拟节点的 Hungarian 最大权部分匹配；低于阈值的边不可采用。展示所选建议及双方竞争候选，不能仅给一个总分。

**首个完整版本中，所有候选分配均需人工接受；只有满足唯一键契约的对应自动成立。** 确定性排序仅保证复现与展示稳定，不证明身份。暂不对每条建议删边重算来证明最优解唯一，也不宣称局部候选差距足以证明全局唯一。未来如增加自动接受策略，必须另行验证误配风险与歧义处理。

### 6.4 分层预算

以下是初始保护预算，未经性能实测，不能写成已支持的数据规模：

| 环节 | 初始保护预算 | 超出后的行为 |
| --- | --- | --- |
| 输入 | 每文件 64 MiB、100000 条逻辑记录、256 列；单元格原始 UTF-8 最多 64 KiB | 输入错误，绝不截断后继续 |
| 剩余候选生成 | 累计去重候选对最多 100000 | 整个剩余候选阶段停止并标记未完成；保留已完成精确对应 |
| 分量求解 | 每个分量每侧最多 100 条记录 | 该分量标记 `unprocessed`，其他可处理分量继续 |
| 编辑距离 | 每字段最多 512 个码点，累计动态规划单元最多 20000000 | 受影响分量及无法在余下预算处理的分量标记 `unprocessed`，不删除昂贵边后伪造完整结果 |

匹配字段数受列数与总预算约束，不再单独限制为四个。处理按稳定顺序进行，昂贵计算和分配前预估成本，防止整数溢出；资源错误必须定位到阶段和范围。

后续用 1000、10000 行的精确核对和不同剩余候选密度测量时间、内存与输出规模，再调整预算并给出机器环境。整表有多少行与复杂候选分量有多大分别报告。

## 7. 人工复核回导

`compare` 生成独立运行目录，包含原始输入快照、规范化配置、引擎版本、指纹清单、对应与差异报告、候选和可编辑决策模板。目录中的输入快照只读使用；保存快照前检查磁盘空间，写入失败不得留下被认为成功的运行结果。原文件始终不修改，输出目录默认必须不存在或为空。

记录标识由左右侧与原始 CSV 逻辑记录号组成，表头不计入记录号；不能用物理文本行号代替含换行字段的逻辑记录号。标识只在当前运行内有效。

支持四种决定：

- `accept(left_id, right_id)`：接受剩余记录的一对一对应；
- `reject(left_id, right_id)`：拒绝指定候选关系；
- `left_unmatched(left_id)`：人工确认左侧记录没有对应；
- `right_unmatched(right_id)`：人工确认右侧记录没有对应。

决定可以填写理由，空白仍为待复核。允许人工指定没有进入候选列表的剩余记录对，但必须给出理由并标为人工覆盖，不伪造通过阈值的评分。精确键已对应的记录被锁定；如需改变其关系，应修改规则重新比较。

`resolve` 执行以下检查与处理：

1. 校验运行标识、输入快照原始字节的 SHA-256、规范化配置指纹和引擎版本；不依赖原路径文件仍然存在。想比较修改后的源文件，必须重新运行 `compare`。指纹用于识别过期/不一致材料，不提供抗恶意篡改认证。
2. 校验记录存在、端点是否已占用、同一对是否同时接受和拒绝、接受与确认无对应是否冲突；完全相同的重复决定可去重，矛盾决定整批拒绝，不局部应用。
3. 拒绝一条候选不等于确认整行无对应；未填写的决定保持待复核。人工接受后仍需按相同规则比较全部内容字段，不能以“接受对应”掩盖字段差异。
4. 从原始运行与累计决定表重新生成最终结果，记录决定来源与理由。重复执行得到相同语义结果，生成时间不参与语义比较；后续复核以原始运行和更新后的累计决定表执行。资源受限的记录也可由人工逐一处置，但未处置记录仍为 `unprocessed`；受限候选计算的历史状态继续保留，不能因手工决定改写为算法已完整运行。

这样用户能够完成复核并带走结果，而不是只能阅读一份“待复核”报告。

## 8. 结果状态、输出和 CLI

记录状态为 `paired`、`unmatched`、`pending_review`、`unprocessed`。`paired` 的来源只能是 `exact_key` 或 `human_review`；`unmatched` 首版表示人工明确确认无对应。候选分配不计入正式配对。

每侧必须满足：配对记录数 + 确认无对应数 + 待复核数 + 未处理数 = 输入记录总数。一条记录只能占一个状态。字段结果为 `equal`、`equivalent_by_rule`、`different`、`invalid_value`；结构问题、忽略列和异常键另行统计。

运行的 `complete/incomplete` 仅表示计算是否完成，不表示人工复核已结束。汇总同时报告计算覆盖、未解决记录、字段问题与结构问题；存在待复核时不得展示“全部对账完成”。人工确认无对应仍属于需要呈现的业务差异，不能因为已有决定就从差异总数中消失。

拟议命令接口（尚未实现）：

```sh
reconcile init-config left.csv right.csv --out rules.json
reconcile check-config rules.json
reconcile compare left.csv right.csv --config rules.json --out run-001
reconcile resolve run-001 --decisions reviewed.csv --out run-001-reviewed
```

`init-config` 仅生成待填写的映射模板，不自动断言主键或类型。`check-config` 检查配置语法与内部一致性；涉及真实列名、输入类型和键唯一性的检查在 `compare` 中完成。

拟议退出码：0 表示计算完整且没有需处理的差异或未决项；1 表示计算完整但仍有字段差异、无对应、无效值、未映射列、异常键或待复核；2 表示输入、配置、决定或 I/O 错误；3 表示资源预算导致未处理。优先级为 2 > 3 > 1 > 0。规则允许的等价变化单独存在时不触发 1。

MoonBit 核心负责配置模型、规则、候选、分配、决策校验和报告数据；文件读取、哈希与终端输出由明确适配层承担。实现前验证适配依赖和目标运行环境，不能把宿主完成的算法宣称为 MoonBit 核心。

## 9. 首版边界

首版支持两份表、显式规则和一对一记录对应。暂不处理拆单/合单、多笔付款对一张订单、自动学习权重、自动猜列或主键、远程数据库、多人协作、自动改写源表、公式重算和任意时区解析。

这些边界用于控制可验证性，不把所有场景强行压成“没有共同 ID 的小表”。XLSX 适配是否需要进入首版，按第 4 节真实输入条件确定。新增功能必须服务已有流程，不能用无关功能数量掩盖需求不足。

## 10. 验证与继续投入条件

**需求验证**：至少记录一个真实流程的来源、现有人工步骤、典型文件规模、规则、误配代价与当前耗时或错误基线。只使用有权处理的数据；敏感原始数据不上传公共平台。三组演示不等于三组真实用户。

**效果比较**：以精确关联加业务规则作为基础对照；候选功能在有人工真值的样例上统计找到的正确对应、错误建议和人工复核负担。增加匹配数量不能单独证明效果改善。无共同键的价值验证不应排除完整精确核对流程本身的价值。

**必要验证覆盖**：

- 列映射、列顺序变化、组合键、重复/缺失键、未映射列和明确忽略列；
- 前导零、十进制容差边界、正负值、无效日期、缺失值与显式状态映射；
- 用独立穷举部分匹配对照小图的最大权结果，覆盖贪心失败、无合格边、同分竞争和未匹配；
- 决策冲突、人工覆盖、指纹不一致、重复回导及未完成决定；
- 记录计数守恒，资源受限不能返回全部成功，输出可追溯至原记录与规则；
- 三个工作流各自从输入到决定回导再到最终报告的完整演示；
- 代表规模和候选密度下的时间、内存、输出体积，以及所用环境和版本。

**继续投入的判断**：有真实流程且能展示相对现有方法的可观察收益则继续；真实输入不兼容先修输入适配或调整定位；现有工具已便捷完成且无新增收益时，暂停独立产品并考虑贡献现有生态。不要为了避免再次被拒而继续堆无关功能。

发布前应有实际测试、可复现运行说明、许可证、依赖与资源边界。测试通过、包发布、重审通过、验收和获奖是不同事实，不能互相代替。
