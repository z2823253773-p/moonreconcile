# Validation limitations

- Every example and benchmark input in Task 7 is synthetic. The adversarial catalog truth set contains one true pair and one false competitor; its rates have no population meaning.
- The independent exact-join-plus-rules reference is narrowly scoped to these fixtures. It is not a general comparator, fuzzy linker, benchmark of a third-party product, or substitute for independent production validation.
- No actual orders, migration, or supplier workflow was observed. Typical file sizes, current manual time, error costs, and decision burden remain unknown.
- Restricted XLSX parsing and conversion code has completed the preceding local implementation tasks, and this activation candidate enables CSV plus restricted XLSX by default. Final Task 7 acceptance still requires the clean activation-SHA full gate, same retained ZIP strict/browser/CLI evidence, independent oracle and final independent whole-branch audit recorded by the controller in the ignored `.superpowers/sdd/2026-10-08-restricted-xlsx/` ledger. The CLI accepts CSV. Excel features outside the frozen restricted subset are rejected; this candidate does not establish interoperability with arbitrary spreadsheets. Whether CSV or the restricted XLSX subset fits a real user's exports is unknown.
- Benchmarks cover only listed deterministic local cases and one machine/toolchain. They do not establish behavior for all inputs, machine sizes, operating systems, or maximum combined workloads. Source parsing tests execute 100000-row boundaries, and the decision replay regression executes 50001+50001 sources with unchanged and cumulative templates; those correctness checks are not throughput benchmarks. Initial configured resource limits are guardrails, not supported-capacity claims.
- Candidate score is not a probability or calibrated confidence. Suggestions require human acceptance; blocking rules can exclude true pairs. The selected assignment can be wrong, as the synthetic catalog case intentionally shows.
- Documentation review does not prove a capability gap against MoonRow, DataComPy, Record Linkage Toolkit, or other software. No competitor comparison run or real-workflow benefit has been established.
- Test completion, a local package check, CI configuration, an actual remote CI result, release publication, contest acceptance, and user value are separate claims. This activation candidate establishes no remote CI or Linux execution result.
- Source tables retain 64 MiB/100000-row/256-column/64 KiB-cell caps. Decision raw templates use 128 MiB/400000 rows with a strict four-column header and the same cell cap; nonblank actions independently use 100000 rows before dedup and 64 MiB canonical CSV including the header. Raw row limits and active row limits have production-constant parser tests. Total-byte boundaries use private reduced limits; no literal 64 MiB active/128 MiB raw or maximum-action end-to-end throughput run was executed.

- The additional OurAirports case uses actual public source snapshots with reproducible hashes and an independent stable-ID/literal-field reference. This demonstrates CSV dataset-version maintenance, not observed customer use, airport accuracy, business explanations, time saving or XLSX export fidelity. Review dispositions are authored and explicitly describe snapshot absence.
- The review-load optimization is a same-driver, single-machine synthetic comparison of pure engine calls. Complete response bytes are compared, including error envelopes in a separate seeded probe. It does not measure filesystem reporting, memory, maximum supported workloads or user effort.
- The precompiled workbench package is designed for Node.js 22 or newer and uses the frozen six-package production closure: direct `buffer-crc32@1.0.0`, `saxes@6.0.0`, `yauzl@3.4.0`, and `yazl@3.3.1`, with transitive `pend@1.2.0` and `xmlchars@2.2.0`. Playwright and browser binaries are development-only. The local offline gate uses macOS `sandbox-exec` to deny outbound networking while allowing loopback; this is environment evidence for the tested run, not a universal OS sandbox or a remote CI result. The Phase A package contract was accepted locally; final activated B acceptance remains pending.

## Frozen native-container compatibility boundary

Full workbook validation rejects real drawings, images, charts, tables, external links and all worksheet formulas (including cached/shared/array/dynamic forms), even outside the selected or visible sheet/range. There is one narrow inert-container exception: at most one drawing part with the exact DrawingML `wsDr` root, no ordinary attributes, no children and only XML whitespace. It must be bound by the sole validated drawing relationship/worksheet marker to the same visible ordinary worksheet that contains an attribute-only `autoFilter ref="A1:B2"`-style bounded rectangle. All inbound relationships to the drawing target count; extra inbound references, outgoing drawing relationships, anchors, comments/processing instructions, filter children/criteria or extra attributes reject. This does not support drawing content or evaluate filters; selected rows remain present with warnings.

An optional static `_xlnm._FilterDatabase` is allowed only as one direct `definedNames` list on the selected ordinary workbook root, with exactly one leaf and precisely the unqualified attributes `name="_xlnm._FilterDatabase" function="false" hidden="true" vbProcedure="false" localSheetId="0"`. Ordinal zero must identify that same validated visible empty-drawing/ref-only-filter owner, whose unique name matches `[A-Za-z_][A-Za-z0-9_]{0,30}`. Its entire decoded leaf text must exactly equal `owner!$COL$ROW:$COL$ROW` constructed from that owner's autoFilter endpoints; no trim, formula parser, alternate rectangle or lookup is used. A candidate list makes real comments and processing instructions unsupported throughout that original workbook XML part. List absence remains allowed. Other named ranges/formulas/constants, Print_Area/Print_Titles and unsupported calculation metadata still reject. The existing exact LibreOffice `extCalcPr` and proven-unused content-type Default exceptions are independent; none bypass full ZIP/XML/relationship/cell validation. These developer restrictions do not select a user's import range or modes.
